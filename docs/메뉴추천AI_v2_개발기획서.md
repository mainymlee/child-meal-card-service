# 한끼 메뉴추천 AI v2 개발 기획서

> 작성일: 2026-08-21  
> 프로젝트: 한끼 아동급식카드 웹앱  
> 개발 단계: 기획 확정 및 1차 개발 착수  
> 기준 시스템: 브라우저 기반 자체 메뉴추천 AI v1

## 1. 개발 목적

메뉴추천 AI v2의 가장 중요한 목적은 **남은 급식카드 예산을 남은 사용 기간에 맞춰 계획적으로 사용하도록 돕는 것**이다. 추천은 단순히 가장 저렴하거나 인기 있는 메뉴를 고르는 것이 아니라, 오늘 사용해야 할 권장 금액과 소멸 예상액을 먼저 계산하고 그 범위 안에서 최근 식사의 영양 균형과 개인 취향에 맞는 메뉴를 선택한다.

AI의 목표 우선순위는 다음과 같다.

1. 남은 잔액을 사용 기간에 맞춰 사용하고 소멸되는 금액을 줄인다.
2. 카드 잔액과 하루 사용 한도를 넘지 않는다.
3. 최근 식사를 고려해 영양과 메뉴 다양성을 보완한다.
4. 만족도 학습으로 개인 취향에 맞춘다.
5. 거리·혼밥·포장 등 이용 편의성을 높인다.

다음 질문에 근거를 가지고 답할 수 있는 시스템을 목표로 한다.

- 왜 이 가게와 메뉴를 추천했는가?
- 이 메뉴를 선택하면 남은 기간의 예산 계획에 어떤 영향을 주는가?
- 사용자의 최근 식사와 만족도가 어떻게 반영되었는가?
- 예산·영업 여부·알레르기 같은 필수 조건을 지켰는가?
- 변경 전보다 추천 품질이 좋아졌는가?

## 2. 현재 AI v1

현재 추천 시스템은 외부 ChatGPT·Claude API를 사용하지 않고 브라우저에서 실행된다.

### 2.1 현재 입력

- 선택 지역
- 영업 여부와 시연 시간
- 혼밥·포장 여부
- 카드 잔액과 예상 메뉴 가격
- 동네 중심점 기준 직선거리
- 최근 식사 7회
- 만족도와 불만 이유 최근 30회
- 결제 실패 제보

### 2.2 현재 처리

1. 지역·영업·메뉴 존재 여부로 후보를 제한한다.
2. 혼밥·포장·예산 조건을 적용한다.
3. 메뉴명으로 영양 특성을 `낮음·보통·높음`으로 추정한다.
4. 최근 음식군 반복, 거리, 가격, 영양, 만족도를 점수화한다.
5. 종합점수가 높은 식당과 가장 적합한 메뉴를 반환한다.

### 2.3 현재 학습

현재의 학습은 신경망 훈련이 아니다. 만족도 기록에 따라 메뉴·음식군·가게와 거리·가격·자극성의 가중치를 조정하는 브라우저 개인화다.

### 2.4 현재 한계

- 추천 점수의 각 항목이 하나의 함수에 섞여 있어 비교와 조정이 어렵다.
- 추천 변경이 실제로 좋아졌는지 판단할 자동 평가 세트가 없다.
- 알레르기와 먹지 못하는 재료를 강제로 제외하지 못한다.
- 메뉴와 가격 대부분이 실제 매장 확인 데이터가 아니다.
- 영양 추정의 신뢰도와 메뉴 데이터 출처가 점수에 충분히 드러나지 않는다.
- 피드백이 없는 신규 사용자의 취향을 알 수 없다.
- 개인화 기록이 브라우저 밖으로 동기화되지 않는다.

## 3. v2 개발 범위

### 3.1 이번 버전에 포함

- 추천 입력과 출력 형식 표준화
- 안전 조건과 선호 조건 분리
- 점수 항목별 계산과 설명 데이터 제공
- 고정 사용자 시나리오 기반 자동 평가
- 최근성·빈도·부정 피드백을 반영한 개인화 개선
- 탐색 추천을 통한 동일 메뉴 고착 완화
- 추천 결과 상위 3개와 이유 제공
- 알고리즘 버전 기록
- 브라우저 내 추천·선택·만족도 이벤트 구조 설계

### 3.2 이번 버전에서 제외

- 외부 생성형 AI API
- 서버 회원가입과 기기 간 동기화
- 여러 사용자의 데이터를 모은 중앙 모델 학습
- 실제 카드 잔액 및 결제 승인 연동
- 질환별 식단 처방
- 검증되지 않은 메뉴 생성

## 4. 핵심 원칙

### 4.1 기간 기반 예산 사용이 최우선

추천 AI는 메뉴 가격을 단순한 최대 한도로만 사용하지 않는다. 다음 값을 이용해 오늘의 적정 지출 구간을 계산한다.

- 현재 남은 카드 잔액
- 사용 가능 기간의 남은 일수
- 하루 권장 사용액
- 하루 사용 한도
- 사용 주기 종료일
- 현재 속도로 사용했을 때 소멸 예상액

```text
오늘 목표 사용액 = 남은 잔액 ÷ 남은 사용 일수
추천 가능 상한 = 남은 잔액과 하루 사용 한도 중 작은 값
예산 적합도 = 메뉴 가격이 오늘 목표 사용액에 가까운 정도
```

너무 비싼 메뉴는 잔액과 한도 초과를 막기 위해 제외한다. 반대로 소멸 위험이 있는데 지나치게 저렴한 메뉴만 반복 추천하지 않도록 오늘 목표 사용액과의 차이를 점수에 반영한다.

추천 결과에는 다음과 같은 예산 이유를 우선 표시한다.

- 오늘 권장 금액 안에서 이용할 수 있어요.
- 남은 기간에 맞춰 잔액을 사용하는 데 적합해요.
- 소멸 예상액을 줄이기 위해 오늘은 이 정도 금액이 좋아요.
- 이 메뉴를 선택하면 오늘 권장액보다 적게 사용해 잔액이 남을 수 있어요.

### 4.2 안전 필터와 순위 모델 분리

필수 조건에 맞지 않는 메뉴는 점수만 낮추지 않고 후보에서 제외한다.

```text
전체 가맹점
→ 안전·필수 조건 필터
→ 추천 가능한 후보
→ 개인화 점수 계산
→ 다양성 재정렬
→ 상위 3개와 추천 이유
```

강제 제외 조건 후보는 다음과 같다.

- 영업 종료
- 메뉴 정보 없음
- 사용 가능 예산 초과
- 사용자가 설정한 알레르기 또는 못 먹는 재료
- 결제 불가가 확인된 가맹점

혼밥과 포장은 결과가 없을 때 완화할 수 있는 선호 조건으로 취급하되, 완화 사실을 사용자에게 알린다.

### 4.3 설명 가능한 추천

모든 결과에 점수 총합만 반환하지 않고 주요 근거를 구조화해 반환한다.

```ts
interface RecommendationReason {
  code: "spending-pace" | "nutrition" | "preference" | "distance" | "budget" | "variety";
  label: string;
  contribution: number;
}
```

사용자 화면에는 점수가 아니라 이해하기 쉬운 이유를 최대 3개 표시한다.

- 최근 채소 섭취가 적어 채소가 포함된 메뉴를 골랐어요.
- 최근 만족한 음식과 비슷해요.
- 예산 안에서 이용할 수 있고 가까워요.

### 4.4 데이터 신뢰도 우선

- 실제 확인 메뉴를 추정 메뉴보다 우선한다.
- 메뉴 출처와 마지막 확인일을 저장한다.
- 신뢰도가 낮은 메뉴는 추천에서 감점하거나 제외한다.
- 실제 메뉴가 아닌 경우 화면에서 예상 정보임을 계속 표시한다.

## 5. 추천 입력 모델

```ts
interface RecommendationContext {
  neighborhood: Dong;

```

사용자 선호 설정은 다음 형태를 목표로 한다.

```ts
interface UserFoodPreferences {
  dislikedKeywords: string[];
  allergyKeywords: string[];

  portion: "small" | "normal" | "large";

```

알레르기 정보가 정확한 원재료 데이터와 연결되지 않은 경우에는 완전한 안전을 보장하지 않으며 매장 확인 문구를 표시한다.

```ts
interface RecommendationResult {
```

추천은 한 개만 반환하지 않고 상위 3개를 제공한다. 사용자가 선택하지 않은 추천도 평가할 수 있도록 결과 순서와 알고리즘 버전을 함께 기록한다.

## 7. v2 점수 설계

초기 v2는 다음과 같이 점수 영역을 분리한다. 정확한 가중치는 평가 결과를 기준으로 조정한다.

```text
최종 점수 =
  기간 기반 예산 사용 점수
  + 기본 적합도
  + 영양 보완 점수
  + 개인 취향 점수
  + 만족도 학습 점수
  + 예산 적합도
  + 거리 적합도
  + 데이터 신뢰도
  - 최근 반복 감점
  - 부정 피드백 감점
```

기간 기반 예산 사용 점수는 동점 해소용 부가 점수가 아니라 최우선 점수다. 다른 선호 점수가 높더라도 잔액 또는 하루 한도를 넘는 메뉴는 추천하지 않는다.

| 영역 | 초기 범위 | 설명 |
|---|---:|---|
| 기간 기반 예산 사용 | -15~20 | 오늘 권장액과 가격 차이, 잔액 소멸 위험 |
| 기본 적합도 | 0~10 | 음식군 기본 품질 |
| 영양 보완 | -8~12 | 최근 식사의 부족·과다 패턴 보완 |
| 개인 취향 | -10~10 | 선호·비선호 반영 |
| 만족도 학습 | -10~10 | 메뉴·음식군·가게 피드백 |
| 예산 안전성 | 강제 필터 | 잔액과 하루 한도 초과 방지 |
| 거리 적합도 | -8~4 | 이동 거리와 거리 불만 반영 |
| 데이터 신뢰도 | -8~4 | 메뉴 출처와 확인일 반영 |
| 반복 감점 | -10~0 | 최근 동일 메뉴·음식군 반복 억제 |

점수 범위는 특정 항목 하나가 전체 추천을 과도하게 지배하지 않도록 제한한다.

## 8. 개인화 학습 설계

### 8.1 학습 이벤트

다음 행동을 서로 다른 강도로 반영한다.

| 행동 | 의미 | 권장 가중치 방향 |
|---|---|---|
| 추천 결과 노출 | 약한 관심 가능성 | 학습하지 않거나 매우 약하게 반영 |
| 상세 화면 열기 | 관심 | 약한 양수 |
| 메뉴 선택 | 선택 의도 | 중간 양수 |
| 식사 완료 | 실제 행동 | 강한 양수 |
| 만족 | 긍정 경험 | 강한 양수 |
| 보통 | 중립 | 변화 없음 |
| 아쉬움 | 부정 경험 | 강한 음수 |

단순 노출을 만족으로 간주하지 않는다.

### 8.2 최근성

최근 피드백에 더 큰 영향을 주되 오래된 취향이 완전히 사라지지 않도록 시간 감쇠를 사용한다.

```text
피드백 영향 = 기본 만족도 × 최근성 가중치 × 행동 신뢰도
```

### 8.3 탐색과 다양성

만족했던 메뉴만 반복하면 새로운 선택을 발견하지 못한다. 상위 3개 중 하나는 다음 조건 안에서 탐색 후보로 제공한다.

- 안전 필터와 예산을 모두 통과
- 최근 반복 메뉴가 아님
- 기존 선호와 너무 멀지 않은 인접 음식군
- 데이터 신뢰도가 낮지 않음

탐색 추천에는 `새로운 메뉴도 하나 골라봤어요`라고 표시한다.

### 8.4 콜드스타트

기록이 없는 사용자는 다음 순서로 추천한다.

1. 기간 기반 오늘 권장액·영업·거리·데이터 신뢰도
2. 백반·정식 등 균형 잡힌 음식군
3. 온보딩에서 선택한 간단 선호
4. 다양한 음식군으로 상위 3개 구성

피드백이 5회 이상 쌓이면 개인화 비중을 단계적으로 높인다.

## 9. 평가 계획

### 9.1 오프라인 고정 시나리오

실제 사용자 데이터 없이도 알고리즘 회귀를 찾을 수 있도록 최소 다음 시나리오를 만든다.

1. 최근 면·국물 반복 → 나트륨이 낮고 다른 음식군 우선
2. 최근 채소 부족 → 채소가 높은 메뉴 가점
3. 특정 메뉴 만족 반복 → 해당 메뉴와 음식군 가점
4. 가격 불만 누적 → 저가 메뉴 우선
5. 거리 불만 누적 → 가까운 가게 우선
6. 반복 불만 → 같은 음식군 감점 강화
7. 메뉴 없는 가게 → 추천 결과에서 제외
8. 예산 이하 메뉴 없음 → 제외 또는 조건 완화 안내
9. 소멸 예상액이 큼 → 지나치게 저렴한 메뉴보다 오늘 권장액에 가까운 메뉴 우선
10. 결제 실패 누적 → 정상 가맹점 우선
11. 신규 사용자 → 특정 업종에 과도하게 몰리지 않음

### 9.2 품질 지표

| 지표 | 목표 |
|---|---|
| 필수 조건 위반률 | 0% |
| 잔액·하루 한도 초과 추천 | 0% |
| 오늘 권장액과 추천 가격의 오차 | 지속 측정 및 감소 |
| 사용 주기 종료 예상 잔액 | v1 대비 감소 |
| 설명 없는 추천 결과 | 0% |
| 메뉴 없는 가게 추천 | 0% |
| 동일 메뉴 연속 추천률 | v1 대비 감소 |
| 사용자 만족 추천 비율 | 데이터 축적 후 v1 대비 증가 |
| 저신뢰 메뉴 노출률 | 지속 감소 |
| 지역·음식군 편향 | 허용 범위 정의 후 모니터링 |

### 9.3 온라인 평가 전제

추천 노출·선택 데이터를 서버에 수집하려면 별도의 개인정보 및 분석 동의가 필요하다. 동의 체계가 마련되기 전에는 브라우저 안에서만 개인화하고 개발용 익명 시나리오로 평가한다.

## 10. 개발 구조 제안

```text
lib/recommendation/
├─ types.ts              입력·출력·점수 타입
├─ eligibility.ts        강제 제외와 조건 완화
├─ features.ts           거리·가격·영양·피드백 특성 계산
├─ scorer.ts             영역별 점수 계산
├─ personalize.ts        사용자 피드백 가중치
├─ diversify.ts          상위 결과 다양성 재정렬
├─ explain.ts            추천 이유 생성
└─ recommend.ts          전체 파이프라인 조립

tests/recommendation/
├─ fixtures.ts           테스트 가게와 사용자 기록
├─ eligibility.test.ts
├─ scoring.test.ts
├─ personalization.test.ts
└─ scenarios.test.ts
```

기존 `lib/ranking.ts`와 `lib/nutrition.ts`는 동작을 유지한 상태에서 단계적으로 새 구조로 옮긴다. 새 엔진이 평가를 통과하기 전에는 운영 추천을 한 번에 교체하지 않는다.

## 11. 개발 단계

### Sprint 1 — 측정 가능한 추천 기반

- 추천 입력·출력 타입 정의
- 잔액·남은 일수·하루 권장액을 추천 입력에 연결
- 기간 기반 예산 사용 점수 분리
- 필수 조건 필터 모듈 분리
- 점수 항목별 결과 반환
- 알고리즘 버전 추가
- 고정 시나리오 테스트 구축
- 기존 v1 결과와 비교 가능한 개발 도구 작성

완료 기준:

- 필수 조건 위반 테스트 0건
- 잔액·하루 한도 초과 추천 0건
- 소멸 위험 시 오늘 권장액에 가까운 메뉴가 우선되는 시나리오 통과
- 모든 결과에 추천 이유 존재
- 기존 주요 추천 흐름의 기능 회귀 없음

### Sprint 2 — 개인화 v2

- 메뉴·음식군·가게 선호 벡터 분리
- 피드백 최근성과 횟수 정규화
- 부정 이유별 가중치 개선
- 콜드스타트 선호 질문
- 상위 3개 다양성 재정렬

완료 기준:

- 만족 피드백 후 관련 후보의 점수가 예상 방향으로 변경
- 가격·거리·반복 불만 시 고정 시나리오 통과
- 같은 음식군의 상위 결과 독점 방지

### Sprint 3 — 데이터 신뢰도와 안전

- 메뉴 출처·확인일·신뢰도 필드
- 알레르기·비선호 설정
- 안전 필터와 경고 문구
- 저신뢰 메뉴 추천 정책

완료 기준:

- 설정한 제외 조건이 모든 추천 진입점에서 동일하게 적용
- 추천 결과에 데이터 신뢰도와 경고 표시
- 추정 메뉴를 실제 메뉴처럼 표현하지 않음

### Sprint 4 — 실제 사용 평가 준비

- 추천 노출·선택·식사 완료 이벤트 구분
- 개인정보 최소 수집 설계
- 사용자 동의와 삭제 정책 문서화
- 운영 지표 대시보드 요구사항 정의

서버 수집은 동의·보안 검토 완료 후 별도 승인된 범위에서만 구현한다.

## 12. 머신러닝 전환 조건

v2의 초기 구현은 설명 가능한 규칙·가중치 모델을 사용한다. 다음 조건을 모두 만족한 뒤 경량 머신러닝 랭킹 모델을 검토한다.

- 실제 확인된 메뉴 데이터가 충분함
- 추천→선택→식사→만족 이벤트가 구분되어 있음
- 익명화된 학습 데이터와 사용자 동의가 있음
- v2 규칙 모델을 기준선으로 평가할 수 있음
- 지역·가격·업종 편향을 측정할 수 있음
- 모델 실패 시 규칙 기반 추천으로 복귀 가능함

첫 모델 후보는 로지스틱 회귀 또는 경량 랭킹 모델이다. 모델은 안전 필터를 대체하지 않고 필터를 통과한 후보의 순서만 결정한다.

## 13. 위험과 대응

| 위험 | 대응 |
|---|---|
| 잘못된 메뉴 데이터 | 출처·신뢰도 표시, 저신뢰 후보 제외 |
| 피드백이 적어 과적합 | 가중치 범위 제한, 기본 추천과 혼합 |
| 한 음식만 반복 추천 | 최근 반복 감점과 다양성 재정렬 |
| 알레르기 정보 누락 | 안전 보장 표현 금지, 매장 확인 경고 |
| 특정 지역·업종 편향 | 시나리오별 노출 분포 측정 |
| 개인 식사 기록 유출 | 브라우저 우선 저장, 서버 도입 전 동의·보안 설계 |
| 알고리즘 변경으로 품질 저하 | 버전 기록, 고정 테스트, v1 복귀 경로 유지 |

## 14. 첫 개발 작업

기획 승인 후 바로 시작할 첫 작업은 Sprint 1이다.

1. `RecommendationContext`, `RecommendationResult` 타입 확정
2. `calcBalancePlan`의 잔액 계획을 추천 입력에 연결
3. 추천 가능 여부를 판정하는 `eligibility` 모듈 작성
4. 기간 기반 예산 사용 점수를 가장 먼저 분리
5. 기존 종합 점수를 영역별 점수로 분리
6. 추천 이유를 점수 근거에서 자동 생성
7. 고정 시나리오 테스트 작성
8. v1과 v2 결과 비교 후 운영 전환 여부 판단

이 순서를 통해 학습 기능을 복잡하게 만들기 전에 추천의 안전성, 설명 가능성, 측정 가능성을 확보한다.
